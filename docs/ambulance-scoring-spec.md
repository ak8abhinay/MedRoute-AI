# Ambulance Suitability Scoring Specification

Version 1 — distillation target. This document is the single source of
truth for ambulance scoring logic. Both `services/dispatchService.js`
(JavaScript, rule-based, production) and `ml-service/train_model.py`
(Python, trains a model to approximate this same function) must conform
to this spec exactly.

## What this scores

Given one emergency and one candidate ambulance, produces a single
continuous suitability score. Higher is better.

## Features supplied to the model (input vector)

All five are provided as input, regardless of whether the current label
formula actually uses each one - see the distinction below.

| Field | Type | Source |
|---|---|---|
| `distance_meters` | float | Real OSRM driving distance, or Haversine fallback |
| `duration_seconds` | float | Real OSRM driving duration, or Haversine-derived estimate |
| `severity` | ordinal: Low=0, Medium=1, High=2 | Emergency.severity |
| `emergency_type` | categorical (one-hot): cardiac, trauma, general | Emergency.emergency_type |
| `has_known_position` | boolean | Whether the ambulance has a non-null latitude/longitude |

## Features that currently influence the V1 label

**Only two of the five supplied features actually affect the score
computed by this formula, verified directly against the live
`scoreAmbulance` function in `dispatchService.js`:**

- `duration_seconds` (only when `has_known_position` is true)
- `has_known_position`

`severity`, `emergency_type`, and `distance_meters` (as a value distinct
from `duration_seconds`) are supplied to the model as input features but
have **zero effect on the V1 label**. This is not an oversight in this
spec — it's an accurate transcription of what `dispatchService.js`
currently does. The rule-based ambulance scorer, as it exists in
production today, only ever considers driving time and whether a
position is known at all.

This is itself worth stating as a finding, not hiding: **the current
rule-based ambulance scorer has fewer meaningful inputs than the
broader system's stated design implies.** A trained model against this
label should correctly learn to (largely) ignore severity and emergency
type for this particular score, since the ground truth it's approximating
does too. If the trained model's feature-importance output does NOT
show duration dominating and severity/type near-zero, that's a signal
something in the training pipeline has drifted from this spec, not that
the model found a hidden pattern.

## Formula (verified, unmodified from the live scorer)
base_score = 100

if has_known_position:
distance_penalty = min(duration_seconds / 45, 40)
else:
distance_penalty = 20

score = base_score - distance_penalty


## Effective output range

Not unbounded in practice, though never treated as a percentage or
probability. With a known position: **60 to 100** (as `duration_seconds`
ranges from 0 to effectively 1800+ seconds, the penalty caps at 40).
Without a known position: **exactly 80** (a flat penalty, no variation).
This narrow, mostly-duration-driven range is itself a property worth
knowing before evaluating the model - it means even a poor model could
achieve a deceptively low MAE by predicting close to the range's
midpoint for everything. R² and the held-out correlation check matter
more here than MAE alone, specifically because of this narrow range.
## Effective output range

With a known position, the score ranges from 60 to 100 because the
duration penalty is capped at 40.

Without a known position, the score is exactly 80.

The relatively narrow output range means MAE should not be interpreted
in isolation. R², held-out correlation, and comparison against the
actual rule-generated scores should also be considered when evaluating
the model.

## V1 vs V2

**V1 (this version): distillation.** Training labels are generated by
running this exact formula - the one above, using only `duration_seconds`
and `has_known_position` - against synthetically generated candidate
data. The model's job is to approximate this specific, narrow function.
It is not learning from real dispatch outcomes.

**V2 (future): outcome-based**, and the point where `severity`/
`emergency_type` might actually start mattering - real outcomes may
reveal that severity SHOULD affect good dispatch decisions even though
today's hand-written rule doesn't encode that. That would be a genuine,
interesting finding V2 could surface that V1 structurally cannot,
precisely because V1 is bound to faithfully reproducing V1's own
label, not to being "smart."

## Explicitly NOT yet part of this spec (V1 scope)

- Crew role/specialty matching, ambulance type/equipment matching -
  not implemented anywhere yet (see project decision log, August 2026).
- Traffic-aware ETA - OSRM is real road-network routing, not live traffic.
- Hospital scoring - a parallel, separate spec will cover
  `hospitalService.js`'s formula (which DOES meaningfully use severity
  and specialty match, unlike this one) once ambulance scoring is proven.
